# รายงานทดสอบภาระ server (13 พ.ย. 2026)

คำถาม 3 ข้อ: **ทำไมช่วงคนเยอะแลค · เครื่องนี้รับได้กี่คน · ถ้าเช่า server ต้องใช้สเปกไหน ราคาเท่าไร**

> สรุปสั้น ๆ
> 1. **ช่วงที่คนเยอะที่สุดจริง (10–12 คน) server ไม่ได้ทำงานหนัก** ใช้ CPU ราว 5% ส่วนใหญ่แลคเฉพาะ **ผู้เล่นบางคน** (ปิงของคนนั้น 2–8 วินาที) ขณะที่คนอื่นในเวลาเดียวกันปิง 10–90 ms ตามปกติ ถ้า server ช้าจริง ทุกคนต้องปิงขึ้นพร้อมกัน สาเหตุจึงน่าจะอยู่ที่เน็ตหรือเครื่องของคนนั้น
> 2. **เครื่องนี้รับได้สบาย ~200 คน** (กระจายหลายแมพ) **เริ่มแลค ~300 คน พังที่ 400 คน** ถ้าทุกคนยืนรวมในเมือง เพดานจะต่ำลงเหลือราว **100–150 คน**
> 3. **Auto Play ใช้แรงเครื่องพอ ๆ กับผู้เล่นที่เล่นเอง** เปิด Auto ข้ามคืนพร้อมกันได้ราว 200 ตัว
> 4. ตอนนี้ยังไม่จำเป็นต้องเช่า server ถ้าจะเช่า แนะนำ **สิงคโปร์ 2 vCPU / 4 GB ราคาราว 800–1,400 บาท/เดือน** ซึ่งพอสำหรับ 100 คน

## 1. แลคเพราะอะไร

### 1.1 ดูจากข้อมูลจริงบน server (อ่านจาก DB อย่างเดียว ไม่ได้แก้)

- คนออนไลน์พร้อมกันสูงสุดที่เคยมีคือ **12 คน** (12 พ.ย. ช่วง 20:30)
- คืนวันที่ 12 พ.ย. ปิงเฉลี่ยของทั้งเซิร์ฟพุ่งเป็นช่วง ๆ ถึง 2–7 วินาที แต่เมื่อแยกดูรายคน:

| ผู้เล่น (ไม่ระบุชื่อ) | ปิงเฉลี่ย | FPS | หมายเหตุ |
|---|---|---|---|
| ส่วนใหญ่ (8–9 คน) | 10–90 ms | 45–143 | ปกติ ในเวลาเดียวกับที่คนอื่นแลค |
| คน A (การ์ดจอรุ่นเก่า) | **~2,000 ms ตลอด 3 ชม.** | 55 | แลคตั้งแต่ตอนที่ในเกมมีแค่ 4 คน |
| คน B (การ์ดจอในตัว) | **~8,500 ms** | 50 | |
| คน C (มือถือ/iPad) | **2,000–8,000 ms** | 20–38 | FPS ต่ำด้วย |
| คน D | 2,000–7,600 ms เป็นพัก ๆ | 130+ | ช่วงอื่นปกติ 66 ms |

**ข้อสรุป:** คำตอบ pong ทุกคนมาจาก server ตัวเดียวกันและคิวเดียวกัน ถ้า server ช้า ทุกคนต้องปิงสูงพร้อมกัน แต่ข้อมูลไม่ได้เป็นแบบนั้น ช่วงที่ "คนเยอะแล้วแลค" จึงเป็น **เน็ตของผู้เล่นบางคน** (มือถือ, Wi-Fi, ISP) และเครื่องที่วาดภาพได้ช้า (FPS 20–38) ไม่ใช่ server และไม่ใช่เน็ตขาออกของบ้าน (ไม่งั้นคนอื่นต้องแลคด้วย) น่าจะเป็นเส้นทางเน็ตของผู้เล่นคนนั้น (รวมถึงเส้นทางของเขาไปถึง Cloudflare)
ข้อมูล DB บอกได้แค่ปิงเฉลี่ยต่อรอบเล่น ดูละเอียดกว่านี้ได้จาก log `[ping]` ของ server จริง ซึ่งบอกปิง FPS เฟรมที่ค้าง และ snapshot ที่ข้ามรายคนทุกนาที

ส่วนที่ทำให้คนเยอะแล้วแย่ลงได้ (ยืนยันจากการทดสอบในข้อ 2):
- **ในเมืองทุกคนเห็นกันหมด** ข้อมูลที่ส่งให้แต่ละคนจึงโตตามจำนวนคนในเมือง ที่ 10 คนใช้ 11 kbps/คน และที่ 100 คนใช้ 66 kbps/คน คนเน็ตอ่อนจะตามไม่ทันเร็วขึ้นเมื่อในเมืองคนแน่น
- **เซฟทุกคนพร้อมกันทุก 30 วิ** เกมจะค้างวูบเท่ากับเวลาเซฟ: 17 ms ที่ 10 คน, 80 ms ที่ 100 คน, 160 ms ที่ 200 คน ยังมองไม่ออกตอนคนน้อย แต่จะเห็นเป็น "กระตุกทุกครึ่งนาที" เมื่อคนเยอะ

### 1.2 เจอเพิ่ม: บน Windows server เดินแค่ ~21 รอบ/วิ แทน 30

โค้ดตั้งให้ server คำนวณเกม 30 ครั้ง/วิ และส่งภาพตำแหน่ง (snapshot) 15 ครั้ง/วิ แต่ตัวจับเวลาของ Windows ละเอียดแค่ ~15.6 ms จึงวัดได้จริงบน server ทดสอบในเครื่องนี้ **21.5 รอบ/วิ** และ **snapshot 10.7 ครั้ง/วิ** (server จริงน่าจะเป็นแบบเดียวกัน หลัง merge ให้ดูยืนยันจากบรรทัด `[perf]`) ผลคือตัวละครคนอื่นและมอนขยับกระตุกกว่าที่ออกแบบไว้ และช้าลงราว 30 ms
เกมยังไม่เพี้ยน (ความเร็วคำนวณตามเวลาจริง) แค่ลื่นน้อยลง ถ้าย้ายไป server Linux ปัญหานี้น่าจะหายเอง

### 1.3 CPU ของ server หมดไปกับอะไร (CPU profile ที่ 300 คน)

| ส่วน | สัดส่วนของงานทั้งหมด |
|---|---|
| สร้าง snapshot และแปลงเป็นข้อความ (JSON) ให้แต่ละคน | ~25% |
| เขียนข้อมูลลงเน็ต + บีบอัด (deflate) | ~15% |
| คำนวณการเดินของผู้เล่นและมอน, AI มอน, ชนสิ่งกีดขวาง | ~30% |
| เซฟลง SQLite | ~5% |
| อื่น ๆ (รับ input, GC, Auto Play) | ส่วนที่เหลือ |

node รันเกมทั้งหมดบน **CPU คอร์เดียว** เครื่องจึงเต็มเมื่อคอร์เดียวเต็ม (เครื่องนี้ i7-10700 มี 8 คอร์ แต่ใช้งานจริงได้คอร์เดียว) ส่วนการบีบอัดใช้คอร์อื่นช่วยได้บ้าง

## 2. จำลองผู้เล่นได้สูงสุดเท่าไร

**วิธีทดสอบ:** สคริปต์ `tools/load-test.ts` เปิด server ทดสอบของตัวเอง (port สุ่ม + DB ชั่วคราว ไม่แตะ server จริงหรือ dev.db) แล้วสร้างบอท Guest ที่ต่อ WebSocket แบบเดียวกับเบราว์เซอร์ (บีบอัด, ส่ง input 30 ครั้ง/วิ, ping ทุก 2 วิ) บอทเดินไปหามอน ตีธรรมดา กดสกิล ใช้ยา ตายแล้วเกิดใหม่ บางตัวเปิด Auto Play
บอทรันแยก process (10 ตัว) ใช้ CPU ไม่เกิน 11% ต่อ process จึงไม่ได้แย่ง server ตัวเลขทั้งหมดวัดจาก process ของ server เอง และแต่ละขั้นวัดค้างไว้ 30 วิ

**เกณฑ์ "เริ่มแลค"** (ตั้งไว้ก่อนวัด) ถ้าเจอข้อใดข้อหนึ่ง:
- server ยุ่งเกิน 70% ของเวลา (เหลือที่ว่างรับช่วงพีคไม่พอ)
- ปิงในเครื่องเดียวกัน (ไม่มีเน็ตคั่น) p95 เกิน 50 ms
- snapshot เว้นช่วงเกิน 250 ms บ่อย (ตัวละครกระตุกจนเห็นได้)

### 2.4 Auto Play กินเท่าไร (200 ตัวกระจาย 4 แมพ)

| | server ยุ่ง | เวลาคำนวณเกม/รอบ | เน็ตขาออก |
|---|---|---|---|
| Auto 0% (ทุกตัวเล่นเอง) | 42% | 6.4 ms | 6.4 Mbit/s |
| Auto 100% | 42% | 7.4 ms | 6.1 Mbit/s |

**Auto Play ใช้แรงพอ ๆ กับคนเล่นเอง** (AI ของ Auto เพิ่มงานราว 0.005 ms ต่อตัวต่อรอบ)
→ **เปิด Auto ข้ามคืนพร้อมกันได้ราว 200 ตัว** ยังสบาย และไม่ควรเกิน ~250 ตัว ถ้ามีคนเล่นปกติด้วย ให้นับรวมกับคนเหล่านั้น

### 2.5 ข้อจำกัดของการทดสอบ
- บอทกับ server อยู่เครื่องเดียวกัน ปิงที่วัดได้จึงไม่รวมเน็ตบ้านและ Cloudflare ปิงจริงคือ ค่านี้ + ปิงเน็ตของผู้เล่น
- บอทส่งทิศทางเดินให้ server คำนวณเอง ส่วนเบราว์เซอร์จริงส่งตำแหน่งมา งานเดินบน server ของบอทจึงอาจมากกว่าคนจริงเล็กน้อย ตัวเลขนี้จึงเอียงไปทางระวัง
- บอทบีบอัดทุกข้อความที่ส่งขึ้นแบบเบราว์เซอร์ (รันซ้ำแบบนี้ที่ 100–400 คน ผลแทบเท่าเดิม: ยุ่ง 28/41/71/100%)
- ไม่ได้ทดสอบแชท ตลาด ห้องบอส หรือปาร์ตี้ ซึ่งทุกอย่างนี้ใช้ CPU น้อย
- เน็ตขาออกที่ต้องใช้ ~33–45 kbps/คน (กระจายหลายแมพ): 100 คน ≈ 3.3 Mbit/s, 200 คน ≈ 6.6 Mbit/s ถ้าเน็ตบ้านอัปโหลดได้ ≥ 20 Mbit/s ก็พอ (**ฝากเจ้าของเช็คความเร็วอัปโหลดของเน็ตบ้าน**)

## 3. ถ้าจะเช่า server

### 3.1 ต้องการอะไร
- **ความเร็วต่อคอร์สำคัญกว่าจำนวนคอร์** เพราะเกมใช้คอร์เดียว คอร์ที่ 2 ช่วยการบีบอัด, SQLite, cloudflared และระบบ
- vCPU ของ cloud แบบแชร์มักช้ากว่า i7-10700 ของเครื่องนี้ต่อคอร์ จึงควรคาดว่ารับคนได้ราว **60–80%** ของตัวเลขในข้อ 2
- ใช้ RAM น้อย (300–700 MB) แค่ 2–4 GB ก็พอ
- ตำแหน่ง: **สิงคโปร์** (ปิงจากไทยราว 20–40 ms) หรือกรุงเทพถ้ามีผู้ให้บริการ
- ข้อมูลรายเดือน (ถ้ามีคนเล่นครบจำนวนตลอด 24 ชม. ซึ่งเป็นกรณีสูงสุด): 50 คน ≈ 0.4 TB, 100 คน ≈ 1.1 TB, 200 คน ≈ 2.2 TB ทุกแพ็กข้างล่างให้ 3–5 TB อยู่แล้ว

| คนพร้อมกัน | สเปกแนะนำ | หมายเหตุ |
|---|---|---|
| 50 | 2 vCPU (แชร์) / 2–4 GB | เหลือเฟือ |
| 100 | 2 vCPU / 4 GB (แบบ dedicated หรือ "CPU-optimized" ถ้าไหว) | แบบแชร์ก็ได้ ถ้าคนในเมืองไม่แน่นเกิน 100 |
| 200 | 4 vCPU dedicated / 8 GB | เกินนี้ต้องแก้โค้ด (ข้อ 4) ซื้อเครื่องใหญ่ขึ้นไม่ช่วย เพราะเกมใช้คอร์เดียว |

## 4. จุดที่แก้ง่ายและได้ผลมาก (เสนอ ยังไม่ได้แก้ รอเจ้าของตัดสินใจ)

| # | แก้อะไร | ได้อะไร | ความยาก |
|---|---|---|---|
| 1 | **ทำ loop ของเกมให้เดินครบ 30 รอบ/วิบน Windows** (นับเวลาสะสมแทนการพึ่งตัวจับเวลา) | snapshot กลับเป็น 15 ครั้ง/วิตามที่ออกแบบ ตัวละครคนอื่นขยับลื่นขึ้น ช้าลงน้อยลง ~30 ms (ใช้ CPU เพิ่ม ~40% แต่ยังเหลือเยอะ) | ง่าย |
| 2 | **เซฟทุกคนใน transaction เดียว** (ตอนนี้แต่ละคนเขียนแยก 2 ครั้ง ซึ่งแต่ละครั้งต้องรอดิสก์) หรือเซฟทยอยทีละไม่กี่คน | กระตุกทุก 30 วิสั้นลงมากหรือหายไป (ตอน 200 คนค้าง 160 ms) | ง่าย |
| 3 | **ในเมือง ส่งข้อมูลเฉพาะผู้เล่นที่อยู่ใกล้สุด ~30–40 คน** หรือส่งตำแหน่งคนไกลถี่น้อยลง | ข้อมูลต่อคนในเมืองไม่บวมตามจำนวนคน คนเน็ตอ่อนเล่นได้แม้เมืองแน่น เพดานในเมืองสูงขึ้นมาก | ปานกลาง (คนไกลอาจหายไปจากจอ ต้องให้เจ้าของเลือกหน้าตา) |
| 4 | snapshot: ไม่ต้องแปลงกระเป๋า/คลังเป็นข้อความทุกครั้งเพื่อเช็คว่าเปลี่ยนไหม · ส่ง event เฉพาะคนในแมพเดียวกัน | CPU ลดลงราว 10–20% | ปานกลาง |

ข้อ 1–2 เป็นงาน server ล้วน ไม่แตะตัวเลขเกม ส่วนข้อ 3 เปลี่ยนสิ่งที่ผู้เล่นเห็น จึงต้องถามก่อน

## 5. เครื่องมือที่เพิ่มใน PR นี้

- **log `[perf]` ใน server** (`server/perf.ts`) พิมพ์ 1 บรรทัด/นาทีเมื่อมีคนออนไลน์ (เครื่องว่างจะไม่พิมพ์) บอก: จำนวนคน/ห้อง/มอน, เวลาต่อรอบเกม (เฉลี่ย/p99/สูงสุด แยกเป็นคำนวณเกม · event · snapshot · เซฟ), จำนวนรอบ/วิ, เวลาเซฟทุกคน, ความหน่วงของ event loop, % ที่ server ยุ่ง, CPU, RAM, เน็ตขาออกจริง (หลังบีบอัด) และ snapshot ที่ข้าม
  ตัวอย่างรูปแบบ (ตัวเลขสมมุติ): `[perf] 12 online · 6 maps/CH · 290 monsters · tick avg 2.1 ms p99 6 max 9 (sim 1.6 · events 0 · snapshots 0.4 · saves 0) · 21.5 ticks/s · autosave max 20 ms · loop lag p99 22 ms max 30 · busy 6% · CPU 8% · RAM 120 MB · out 400 kbit/s (JSON 6 Mbit/s, 260 msg/s)`
  ตั้ง `PERF_LOG_MS` เพื่อเปลี่ยนความถี่ และ `PERF_JSON=1` เพื่อให้พิมพ์แบบ JSON สำหรับสคริปต์
- **สคริปต์บอท** `tools/load-test.ts` (ไม่อยู่ใน `npm run test`)
  ```
  node --import tsx tools/load-test.ts --scenario spread --steps 25,50,100,200 --hold 30 --auto 0.5 --hub 0.2 --workers 10
  ```
  `--scenario hub|one|spread` · `--auto` สัดส่วนที่เปิด Auto · `--hub` สัดส่วนที่อยู่ในเมือง · `--prof` อัด CPU profile · `--out ไฟล์.json`
  สคริปต์เปิด server ทดสอบเองทุกครั้ง (port สุ่ม + DB ชั่วคราว) แล้วปิดเองเมื่อเสร็จ
